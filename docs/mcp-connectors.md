# MCP connectors: Claude, Gemini, and Grok

The public CPTR MCP endpoint is provider-neutral. Claude, Gemini, and Grok must discover the same RFC 9728 protected-resource metadata and OAuth authorization-server metadata, then authenticate using authorization code + PKCE with the MCP resource indicator.

Do not create provider-specific OAuth implementations. Provider differences belong in client registration metadata: callback URIs and `application_type`.

## Connector bootstrap

When a client accepts an explicit OAuth client ID, register a public client against the deployed authorization server:

```bash
CPTR_DEPLOYED_MCP_URL="$CPTR_DEPLOYED_MCP_URL" \
CPTR_CONNECTOR_NAME="$CPTR_CONNECTOR_NAME" \
CPTR_CONNECTOR_REDIRECT_URIS="$CPTR_CONNECTOR_REDIRECT_URIS" \
CPTR_CONNECTOR_APPLICATION_TYPE="$CPTR_CONNECTOR_APPLICATION_TYPE" \
npm run connector:register
```

Required values come from the actual deployed MCP endpoint and the target client's connector UI/runtime. Do not guess callback URIs. Hosted callbacks use `application_type=web`; localhost or loopback callbacks use `application_type=native`.

The command performs standards-based discovery from the MCP `401` challenge, verifies RFC 9728/OAuth metadata and PKCE S256, performs Dynamic Client Registration, and returns a reusable public `client_id`. It deliberately does not print or depend on a client secret.

## Automatic OAuth clients

Clients that implement MCP OAuth discovery and DCR can be configured with only the public MCP URL. The server advertises:

- RFC 9728 protected-resource metadata
- OAuth authorization-server metadata
- authorization-code flow
- PKCE S256
- refresh tokens
- Dynamic Client Registration
- CIMD support in native OAuth mode
- RFC 8707 resource binding
- RFC 9207 `iss` in authorization responses

## Production qualification

Production qualification must use the real client callback metadata rather than treating every connector as a native application. Supply structured connector profiles through `CPTR_EDGE_DCR_CLIENTS_JSON`:

```bash
CPTR_DEPLOYED_MCP_URL="$CPTR_DEPLOYED_MCP_URL" \
CPTR_EDGE_AUTH_MODE="$CPTR_EDGE_AUTH_MODE" \
CPTR_EDGE_DCR_CLIENTS_JSON="$CPTR_EDGE_DCR_CLIENTS_JSON" \
npm run check:public-edge
```

`CPTR_EDGE_DCR_CLIENTS_JSON` is a JSON array. Each entry contains `client_name`, `redirect_uris`, and optionally `application_type`. If `application_type` is omitted, the verifier infers `native` only when every callback is HTTP loopback; all other valid callbacks are treated as `web`.

The legacy `CPTR_EDGE_DCR_REDIRECT_URIS` input remains supported. Each URI is qualified independently and its application type is inferred instead of being hardcoded.

## Provider behavior

Claude custom connectors can use a remote MCP URL and perform OAuth; deployments that expose advanced OAuth client settings can use a client ID generated by `connector:register`.

Gemini CLI supports remote MCP OAuth discovery and token management. Because client-version behavior can differ, `connector:register` provides a deterministic fallback when an explicit client ID is required.

Grok custom MCP connectors accept a public remote MCP URL and complete required authentication through the connector flow. The public-edge gate should include the exact callback metadata observed from the deployed Grok connector before release approval.

## Security boundary

Do not change the production OAuth topology merely to make one provider connect. Cloudflare Managed OAuth and native OAuth are separate deployment modes. Preserve the selected mode, keep `/mcp` resource binding exact, and fix callback/application-type policy at the registration boundary.
